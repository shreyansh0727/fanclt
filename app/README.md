# FanCtl mobile app

Expo + React Native + TypeScript client for the FanCtl controller.

- Firebase Auth (email/password) signs you in; REST calls use that ID token, and the Realtime
  Database client uses the same session.
- Controls go **LAN first**: if the phone is on the same network as the ESP32, commands are
  sent straight to `http://<device-ip>/api/command` with the device's local key (about 10 ms).
  If that fails or times out after 1.5 s, the same command goes through FastAPI, which writes it
  to the controller's Realtime Database node; the device id is put on a 60 s LAN cooldown so taps
  stay snappy.
- Live state comes from `firebase/database`: one `onValue` listener per paired controller on
  `devices/<id>`, plus `.info/connected`. The store applies optimistic updates on tap and
  reconciles with what the controller writes back.

## Configure

Copy `.env.example` to `.env` — Expo loads it automatically. Values override the
placeholders in `app.json` (`expo.extra`), which remain as fallback defaults.

| Variable | Value |
| --- | --- |
| `EXPO_PUBLIC_API_BASE` | `http://<PC-LAN-IP>:8000` while developing, `https://api.example.com` in production |
| `EXPO_PUBLIC_FIREBASE_API_KEY` | Firebase web app `apiKey` |
| `EXPO_PUBLIC_FIREBASE_AUTH_DOMAIN` | `<project>.firebaseapp.com` |
| `EXPO_PUBLIC_FIREBASE_PROJECT_ID` | Firebase project id |
| `EXPO_PUBLIC_FIREBASE_APP_ID` | Firebase web app id |
| `EXPO_PUBLIC_FIREBASE_DATABASE_URL` | `https://<project>-default-rtdb.firebaseio.com` (live state) |
| `EXPO_PUBLIC_AUTH_EMULATOR` | `http://<PC-LAN-IP>:9099` to sign in against the local Auth emulator; blank for the real project |
| `EXPO_PUBLIC_RTDB_EMULATOR` | `http://<PC-LAN-IP>:9000` to stream from the local database emulator; blank for the real database |

With `EXPO_PUBLIC_AUTH_EMULATOR` set, `src/firebase.ts` calls `connectAuthEmulator`, so
accounts are created in the emulator. `EXPO_PUBLIC_RTDB_EMULATOR` wires `connectDatabaseEmulator`
(host and port only) and still needs `EXPO_PUBLIC_FIREBASE_DATABASE_URL` for the namespace. Any
non-empty `apiKey` works in emulator mode; the `projectId` must match the backend's
`FANCTL_PROJECT_ID` (`hrllo-530fe`) or the server will reject the tokens and the rules will
reject the database reads. Live views stay static if no database URL is set.

If the Firebase values are still empty the app boots into a configuration notice
instead of crashing.

## Run

```bash
cd app
npm install
npx expo start
```

- Physical phone: same WiFi as the PC, and the PC firewall must allow inbound TCP 8000
  (backend), 8081 (Metro), 9099 (Auth emulator), 8080 (Firestore emulator) and 9000 (database
  emulator).
- Android emulator: `EXPO_PUBLIC_API_BASE` cannot be `127.0.0.1` (that is the emulator
  itself). Use the host machine's LAN IP, or `10.0.2.2` with the backend bound to `0.0.0.0`.
- The emulators must listen on the LAN, not localhost — `firebase.json` sets
  `host: "0.0.0.0"` for auth, firestore and database, and `firebase emulators:start` picks it up.
- Live state needs the app's database URL/emulator to point at the same database the backend
  writes to; otherwise the device list loads but tiles never update.
- LAN control needs the phone on the same subnet as the controller. When it is not, the app
  shows a `No LAN` pill and goes through the cloud.
- Restart Metro with `npx expo start -c` after editing `.env`, because `EXPO_PUBLIC_*`
  values are inlined into the bundle at build time.

Type check:

```bash
npm run typecheck
```

## Build an APK (Windows)

```bash
npx expo prebuild --platform android
cd android
./gradlew assembleDebug
```

Output: `android/app/build/outputs/apk/debug/app-debug.apk`, signed with the debug key. It still
loads JS from Metro, so keep `npx expo start` running; `assembleRelease` bundles the JS and needs
a keystore.

The SDK ships CMake 3.22.1 with ninja 1.10, which rejects object paths longer than 260 characters.
This repo's path is deep enough to hit that in the generated codegen targets, so the build needs a
newer ninja next to a private CMake copy, selected with `android/local.properties`. Run these from
`app/` after prebuild:

```bash
../.venv/Scripts/pip.exe install ninja            # any ninja >= 1.11
cp -r "$LOCALAPPDATA/Android/Sdk/cmake/3.22.1" C:/cm
cp ../.venv/Scripts/ninja.exe C:/cm/bin/ninja.exe
printf 'sdk.dir=C\\:/Users/<you>/AppData/Local/Android/Sdk\ncmake.dir=C\\:/cm\n' \
  > android/local.properties
```

`android/` is gitignored (it is regenerated by prebuild), so recreate `local.properties` after a
fresh prebuild.

## Screens

| Screen | Purpose |
| --- | --- |
| Auth | Sign in / create account |
| Devices | Controller list, live connection dot, pull to refresh, sign out |
| Device | Master on/off, 8 channel tiles (tap toggles, long-press renames and sets type), telemetry, identify, remove |
| AddDevice | Pairing-code entry and claim |
| Schedules | Create/delete schedules and pause them; each runs on the backend even when the app is closed |

## Layout

```
App.tsx                     Navigation shell + unconfigured-Firebase notice
src/config.ts               apiBase, Firebase config, database URL/emulator, timeouts
src/firebase.ts             Guarded SDK init (Auth persistence + database handle)
src/lib/api.ts              Authenticated REST client with typed errors
src/lib/local.ts            Direct-to-device HTTP client with cooldown
src/lib/live.ts             Per-device Realtime Database listeners + .info/connected
src/lib/store.tsx           Auth, devices, optimistic commands, LAN→cloud transport
src/lib/types.ts            API types (mirror of backend/models.py)
src/components/             Button, Pill, ChannelTile
src/screens/                Five screens above
```

## Notes

- There is no offline queue. A command issued while offline comes back as
  `acked: false, online: false` and the tile snaps back.
- `lan_key` is the same secret the device uses for its cloud commands. It is only returned to
  the owner by the backend; never log it.
- Live data is read from `devices/<id>` in the Realtime Database; Firestore client access
  stays denied. Ownership is enforced by rules (the node's `owner` must equal your uid).
